## Summary
Six targeted fixes to job search: salary formatting, message wording, a destructive early-return in `FindJobsPage`, a new content-based dedup signature in `agent/adzuna.ts`, a scoring rubric, and `temperature: 0`. Five of the six are small, well-reasoned, and covered by tests that were mechanically updated to match. The sixth — the new `jobSignature` dedup — is the one genuinely new piece of logic in this diff, and it has a real correctness gap: it omits location, so two distinct job postings (same company, same title, same rounded salary, different city) will silently collide and one will never be inserted, with no logging and no way for the user to notice. That logic, and the `FindJobsPage` fix for the table-wiping bug it's paired with, both ship with zero test coverage, executing or source-contract, in a codebase that otherwise tests this exact file and function pattern extensively.

## Blockers

### 🔴 `jobSignature` omits location, so a real posting can be silently merged away, `lib/job-signature.ts:14`
**Problem**: `jobSignature(company, title, salary)` keys only on employer, title, and formatted salary. `agent/adzuna.ts:135-146` uses it to skip inserting any job whose signature already exists, either seeded from the database (`agent/adzuna.ts:99-124`) or added in-loop from earlier jobs in the same batch (`agent/adzuna.ts:187`). Location — already available on every `AdzunaJob` as `job.location.display_name`, and already written to the `location` column two lines below the skip — is not part of the key. Two openings that are genuinely different postings (the same title, at the same company, for the same or absent salary, in two different cities — a routine pattern for multi-location roles and for remote-friendly postings with a company-wide salary band) hash to the same signature. The second one is silently dropped: no error, no log, `jobsFound` simply doesn't count it, and there is no code path by which the user ever sees it.
**Why it matters**: The stated goal of this change was to fix visible duplicates without discarding real jobs (see the caller's own comment at `agent/adzuna.ts:93-98`, "the same role at the same company for the same money arrives as two distinct rows" — an assumption about *duplicate* postings, not distinct ones). A false merge is worse than the duplicate it replaces: a duplicate is merely annoying, a false merge is a job the user should have been able to see and apply to, silently absent, indistinguishable at the UI or API level from "Adzuna didn't return it." This is exactly the class of defect the rest of this diff (and the README's own "outage" postmortem) was written to stop happening. The test suite for `jobSignature` (`tests/job-signature.test.mjs`) is real and execution-based, but every case in it varies company, title, or salary — none holds those three fixed and varies only location, so this exact failure mode is untested and would pass today.
**Suggested fix**: Include location in the signature (Adzuna's `location.display_name` is already fetched and stored), or, if cross-location collisions are meant to be treated as the same opening, say so explicitly in the comment and add a test that pins that decision instead of leaving it implicit and untested.

## Major

### 🟠 The new signature-dedup logic in `agent/adzuna.ts` has no test coverage, executing or source-contract, `agent/adzuna.ts:93-146`
**Problem**: `tests/agent-adzuna.test.mjs` was touched in this diff only to update the `formatSalary` regex. None of the ~40 new lines in `runJobSearch` — the `existingSignatures` seeding query (`company, title, salary` scoped by `.in("company", ...)`), the skip check, or the "add to the set on insert" comment's own claim that in-batch duplicates are caught — has any assertion, not even the source-contract regex style this file uses for every other branch (the external-id dedup added in a prior change has four dedicated tests at lines 138-183 of that file covering ordering, the empty-array guard, and that it isn't done by filtering). `tests/job-signature.test.mjs` tests the pure function in isolation; nothing exercises its wiring into `runJobSearch`.
**Why it matters**: Per the test signal for this project, new branching logic with no test update is at minimum a Minor, a Major when it's branching logic that affects what data reaches the user — which this is. It's also the one piece of new logic in this diff that isn't a straight text/formatting change, and it's the one with the correctness bug above. A source-contract test asserting the query shape, the seed-then-add ordering, and the empty-array guard (mirroring the existing external-id tests) would have been cheap and consistent with the codebase's own convention, and a behavioral test on `jobSignature`'s integration point would likely have caught the location gap.
**Suggested fix**: Add coverage mirroring the existing external-id dedup tests: the seeding query's shape and scoping, that it runs before the loop, that the skip happens before scoring, and — ideally — a test that exercises two jobs differing only in location to pin whether that's an intended merge or a bug.

### 🟠 The `FindJobsPage` fix for the table-wiping bug ships with zero test coverage, `components/find-jobs/FindJobsPage.tsx:162-169`
**Problem**: The early return that used to fire `setJobs([])` on `jobsFound === 0` — described in the task context as wiping "a table that may hold dozens of saved jobs" — is gone, replaced with an unconditional refetch and `setStatus(rows.length === 0 ? "empty" : "success")`. `tests/find-jobs-contract.test.mjs`, the file that source-contract-tests essentially every other line of this component (refetch ordering, refetch-error handling, the empty/error/success states, focus-visible treatment down to a count of `focus-visible` occurrences), was not touched by this diff and has no assertion that the destructive early return is gone or that status is now derived from `rows.length` rather than `result.jobsFound`.
**Why it matters**: This is the fix for the most severe bug in the batch by the task's own description (an all-time list getting wiped on a no-op search) and the only one of the six with no test — before or after — anywhere in the suite. Nothing here would catch a regression that reintroduced the early return, or a future edit that swapped `rows.length === 0` back for `result.jobsFound === 0`.
**Suggested fix**: Add a source-contract test in `tests/find-jobs-contract.test.mjs` asserting the pattern is gone (e.g. `doesNotMatch` on `jobsFound === 0` followed by `setJobs([])`) and that `setStatus` is driven by `rows.length`, consistent with how the file already tests the refetch-error and thrown-error paths.

## Minor

### 🟡 `temperature: 0` may reinforce, not fix, the round-number clustering the rubric is fighting, `agent/matcher.ts:70` and `agent/matcher.ts:22`
**Problem**: `temperature: 0` makes decoding greedy: at every token, the model emits its single highest-probability continuation. The new rubric explicitly anticipates that this highest-probability token for a "score" is often a round number ("Multiples of five are not preferred, and a score of exactly 70 or 75 is almost never the most accurate answer"). Determinism (bug f, reproducible scores for the same input) and de-clustering (bug e, use the whole range) are two different problems, and the fix picked for the first (greedy decoding) is the sampling mode most prone to the failure mode of the second. It's plausible the prompt instruction is enough to shift the greedy path away from round numbers, but it's also plausible it isn't, and nothing in this diff (or the test suite, which only asserts the prompt text and the literal `temperature: 0`) exercises real model output to check either way.
**Why it matters**: If the rubric instruction doesn't fully override the round-number bias under greedy decoding, this diff fixes the reproducibility bug (f) while leaving the clustering bug (e) only partially addressed, and there'd be no signal in CI to reveal it — only another round of "driving the real app and inspecting production data."
**Suggested fix**: No action required before merge given this can't be verified without a live call, but worth a note to check score distribution in production data after this ships, the same way the original clustering bug was found.

### 🟡 `.in("company", ...)` seeding query has no time bound and grows with the account's history, `agent/adzuna.ts:99-124`
**Problem**: The signature-seeding query matches every row the user has ever saved for any company appearing in the current Adzuna batch, with no date filter and no limit. For a recurring, common employer (Google, Amazon, etc.) that a user searches for repeatedly over months, this query's row count grows with the user's total saved-job history at that employer, not with anything scoped to the current search.
**Why it matters**: In practice this is soft-bounded by the free-tier usage cap (10 searches/30 days per `docs/specs/0018-free-tier-usage-gating.md`), so it's unlikely to become a real performance problem at current scale, and there's no index on `company` to make it worse than a sequential scan already would be. Flagging as a "worth revisiting if usage caps ever loosen" note, not a blocking concern.
**Suggested fix**: None needed now; if usage caps change, consider scoping this by a recency window or adding an index on `(user_id, company)`.

### 🟡 The "no new jobs" message overclaims when Adzuna returned nothing at all, `app/api/agent/find/route.ts:126-129`
**Problem**: `jobsFound === 0` always renders "No new jobs. Every result was already in your list." This is accurate when Adzuna returned results that were all duplicates, but the same code path also fires when Adzuna's search returned zero results in the first place (an obscure title/location combination), in which case nothing was "already in your list" — there was nothing to compare against.
**Why it matters**: Minor, cosmetic wording inaccuracy in the case that motivated this fix in the first place (message contradicting what actually happened). Low impact since a genuinely-empty account still shows the distinct "empty" state via `FindJobsPage`, but a returning user with existing jobs and an obscure search would see a slightly misleading claim.
**Suggested fix**: Track whether `adzunaJobs.length === 0` separately in `runJobSearch`'s return value and branch the copy on that, or soften the wording to something true in both cases (e.g. "No new jobs from this search.").

### 🟡 `z.number().catch(0)` now collides with a legitimate score band, `agent/matcher.ts:7` and `agent/matcher.ts:21`
**Problem**: Pre-existing behavior, not introduced by this diff: if the model returns JSON that parses but has a non-numeric `matchScore`, `jobMatchSchema`'s `.catch(0)` silently substitutes `0`. Before this diff, real scores clustered at 60-75 (per the bug being fixed), so a `0` in the data was a clear anomaly, likely how "some existing jobs rows have `match_score = null`" was even noticed. The new rubric explicitly makes `0-29` ("a different discipline, or clearly unqualified") a legitimate, intended output. A schema-fallback `0` and a genuine bottom-of-range score are now indistinguishable from the stored value alone.
**Why it matters**: Not a new bug, but the rubric change quietly removes a diagnostic signal that helped catch a previous silent-failure class in this exact codebase. `matchReason` would be `""` on the fallback path vs. a real explanation on a genuine low score, so it's still recoverable by inspection, just no longer obvious from the score column alone the way it used to be.
**Suggested fix**: Not required for this diff, but worth using a sentinel that can't collide with a valid score (e.g. `null`, matching the sibling failure path in `agent/adzuna.ts:159`) rather than `0`, the next time this file is touched.
