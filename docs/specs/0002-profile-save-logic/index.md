# 0002. Profile save logic

**Date**: 2026-07-23
**Status**: Accepted

## Summary

This decision wires the already built Profile page (feature 05, mock data only) to the real database. Selecting a resume now uploads that file to storage right away, before Save Profile is ever clicked, so the person gets fast feedback that it worked. The form's other fields, and the resume's link to the person's profile row, still only save when Save Profile is clicked, one deliberate save moment for the actual record, same as before. A single shared rule computes how complete a profile is. No database migration is needed. Storage stays the trickiest part: the resume bucket is private, so the app stores the file's key, not a URL, and fetches a short lived link only when it actually needs to show one. This is a second revision of the original combined save decision; see Rationale for why the resume upload timing changed. A third, smaller revision makes that staged, not yet saved upload survive a page refresh within the same browser tab, so refreshing no longer makes an already uploaded file look like it vanished.

## Requirements

**User stories**:
- As a signed in user, I want to edit my profile and have it actually save, so my information is there the next time I visit.
- As a signed in user, I want to see how complete my profile is and exactly what is missing, so I know what to fill in next.
- As a signed in user, I want my resume to start uploading the moment I pick it, so I find out right away if something is wrong with the file, without waiting until I click Save Profile.

**Acceptance criteria** (the contract, each criterion is IDed and independently checkable):
- **AC-1**: Saving the profile form persists every editable field to the signed in user's `profiles` row, scoped by row level security, and the saved values are still there after a page reload.
- **AC-2**: `job_titles_seeking` and `preferred_locations` round trip correctly between the form's comma separated text and the database's array columns (split, trim, drop empty entries on save; comma join on read back).
- **AC-3**: The completion percentage, the missing field labels, and the persisted `is_complete` flag are all computed from one shared rule, in one place, never duplicated between the save action and the page that renders the banner.
- **AC-4**: A resume PDF selected or dropped in the upload area is uploaded to storage right away, not held until Save Profile is clicked. The server enforces PDF only and a 5MB limit itself on this upload, not just through the file picker's filter. The key storage returns for this upload is not written to `resume_pdf_url` until Save Profile is clicked; at that point it is written in the same database write as the rest of the profile fields, and a previous resume, if one existed, is removed from storage only after that write succeeds.
- **AC-5**: A brand new user with no `profiles` row yet sees an all empty form at 0% complete. Clicking Save Profile, with or without a newly uploaded resume, creates that row; there is no separate "create the row first" step.
- **AC-6**: Both the resume upload action and the save action re-check that the caller is actually signed in (never assume the page level redirect already handled it), and always return a structured result (success plus the fields the caller needs, or success `false` plus a human readable error). The save action refreshes the profile page's data after a successful write.
- **AC-7**: The `profile_completed` analytics event fires exactly once, the moment a profile's `is_complete` flag flips from false to true, not on every later save of an already complete profile. The resume is not one of the ten fields that count toward completion, so nothing about this timing change affects when or whether this event fires.
- **AC-8**: Selecting or dropping a resume without ever clicking Save Profile does not change the person's `profiles` row at all (`resume_pdf_url` stays whatever it already was). The file itself, though, is already sitting in storage from the moment it was selected, not yet linked to any row. Picking a different file before ever saving deletes that earlier, still unlinked upload on a best effort basis. Leaving the page after selecting a resume and never saving leaves that one upload behind in storage, unreferenced by anything; this is an accepted tradeoff, not a defect. A refresh of the same tab is not "leaving the page" for this purpose; see AC-10.
- **AC-9**: Both Save Profile and the resume control itself are disabled while a resume upload triggered by the current selection is still in flight, so a save can never fire with a resume that has not actually finished uploading yet, and a second file can never be picked before the first one has resolved.
- **AC-10**: A resume that finished uploading but was never saved (Save Profile not yet clicked) still shows as uploaded, ready to save, after refreshing the same browser tab; refreshing never re-uploads it and never writes anything to the `profiles` row by itself. This survives a refresh only, scoped to that one tab: closing the tab, or opening the profile page in a different tab or browser, still starts from nothing selected, the same accepted tradeoff AC-8 already describes. Signing out and a different person signing in on the same tab must never show the first person's staged resume.

## Decision

**Chosen option**: Option 1 stays for the rest of the form: one combined save action for every field. The resume itself now splits out, uploading immediately on select rather than waiting for that save.

`actions/profile.ts` exports two Server Actions. `uploadResumeFile(file, previousUnsavedKey?)` runs the moment `ResumeUpload` reports a newly picked file: it re-checks the caller is signed in, enforces PDF only and the 5MB limit server side, uploads to a fresh unique key, and, when `previousUnsavedKey` is given, best effort deletes that key too (its own upload attempt is never blocked or failed by that cleanup call failing). It returns the new key on success. `saveProfile(profile, resumeKey)` keeps its old shape and its old job for every other field, except `resumeKey` is now either `null` (no new upload this session) or the key an earlier `uploadResumeFile` call already returned, never a raw `File`; `saveProfile` no longer touches storage to upload anything, it only decides whether to write that key into `resume_pdf_url`. Backed by the same two small shared pure helper modules for field mapping and completion as before.

Storage does not overwrite an existing key; uploading to a key that already exists succeeds under a renamed key instead (confirmed directly against the live backend, see Rationale). Rather than lean on that undocumented renaming behavior, each resume upload, whether from `uploadResumeFile` or a later replace, targets a fresh, unique key, `${userId}/<a random id>.pdf`, never the fixed `${userId}/resume.pdf`. A unique key never collides, so there is nothing to rename and the response's key always equals the one requested; the app still stores whatever key the response actually returns, as a cheap safety net, not because it expects it to differ.

Before writing anything, `saveProfile` still reads the caller's current `profiles` row first (by `id`, the same row it is about to write). This one read serves the same two needs as before: the previous `resume_pdf_url`, if any, to delete once the new write succeeds, and the previous `is_complete` value AC-7 needs to detect the false to true transition. Replacing an already saved resume is therefore: read old key, write the new key (already uploaded by `uploadResumeFile` earlier) to `resume_pdf_url`, then delete the old key. This order still means a failed write never costs the user their existing resume; the only thing that moved is that the upload itself now happens earlier, outside this function.

Uploading on select, rather than on save, means `ResumeUpload` now has real asynchronous work of its own (uploading, succeeded, failed), not just a `File` to hand off. `ResumeUpload` stays a presentational component: it still only reports the raw selected `File` up through `onFileSelected`, plus now renders whatever upload state it is given as props. The actual `uploadResumeFile` call, and the `resumeKey` it resolves to, live in `ProfileEditor`, the same wrapper that already coordinates `ResumeUpload` and `ProfileForm` for `saveProfile` (see Feature design). `ProfileEditor` also holds onto the previous, not yet saved key so a reselect before Save Profile can pass it as `previousUnsavedKey` and clean itself up; that state is cleared, not carried into cleanup logic, the moment `saveProfile` actually succeeds, since at that point the key is a real, saved resume, not an abandoned upload.

A reselect while the current upload has not yet resolved would otherwise be a real race: the earlier upload's key might not exist in state yet to hand to `previousUnsavedKey` (leaking it), or two in flight uploads could settle out of order and leave the wrong, older key as the one Save Profile ends up writing. `ResumeUpload`'s input and dropzone are disabled for the whole time an upload is in flight, the same lock AC-9 already puts on Save Profile, which rules this out structurally: a second file can never be picked before the first one has resolved, so at most one `uploadResumeFile` call is ever in flight at a time and `previousUnsavedKey` is always the one real previous key.

**Third revision, surviving a refresh (AC-10):** `resumeKey` and `resumeFileName` lived only in `ProfileEditor`'s React state, so a refresh lost them even though the file itself was already sitting in storage, still valid. `ProfileEditor` now mirrors both values into `sessionStorage`, under a key namespaced by the signed in user's id (`profile-staged-resume:${userId}`), every time `uploadResumeFile` resolves successfully, and clears that entry the moment `saveProfile` actually succeeds, the same instant it already clears the React state. `sessionStorage`, not `localStorage`, on purpose: it is scoped to one tab and cleared when that tab closes, so a second tab or a later browser session always starts clean, matching AC-10's stated scope exactly (survive a refresh, nothing wider) without having to reason about two tabs racing each other. Namespacing the key by user id is what keeps a different person signing in on the same tab from ever reading the first person's entry; no separate sign out hook is needed, since a different signed in user reads a different, never yet written key.

Reading that entry back is not as simple as an ordinary client only read, because `ProfileEditor` is a Client Component that Next.js still renders on the server first. The server has no `sessionStorage` at all, so the server rendered HTML always reflects "nothing staged." If `resumeKey`/`resumeFileName` were initialized straight from `readStagedResume(userId)` inside the `useState` call itself, the client's first render would disagree with that server rendered HTML the instant something actually is staged, a real hydration mismatch, not a cosmetic one. The state must instead start at `null`, exactly like the server render, and the rehydration read must happen in a `useEffect` that runs once after mount, updating state a moment after the page first paints. In practice this means a person refreshing onto a genuinely staged resume sees the dropzone in its idle state for one frame before it flips to "uploaded," not an instant, flicker free restore; a small, acceptable cost for staying hydration safe.

Nothing else in the design changes. A rehydrated `resumeKey` is just a `string`, indistinguishable from one this render's own `uploadResumeFile` call just resolved: `saveProfile` writes it exactly the same way, and a reselect after rehydrating passes it to `uploadResumeFile` as `previousUnsavedKey` exactly the same way, so the existing best effort cleanup already covers "replace a resume that survived a refresh" with no new code.

## Feature design

**Data model sketch**:

No migration. Reuses the existing `profiles` table from spec 0001 exactly as is. This feature's job is to populate these columns correctly, not to change any of them:

| Column | Written by | Note |
|---|---|---|
| `id`, `email` | `saveProfile` | always taken from the server side session, never trusted from client input |
| `full_name`, `phone`, `location`, `current_title`, `experience_level`, `years_experience`, `skills`, `industries`, `work_experience`, `education`, `job_titles_seeking`, `remote_preference`, `preferred_locations`, `salary_expectation`, `linkedin_url`, `portfolio_url`, `work_authorization` | `saveProfile` | |
| `resume_pdf_url` | `saveProfile`, only when `resumeKey` is not null | holds the storage object key, not a URL. `uploadResumeFile` produces the key when a file is selected, ahead of any save; `saveProfile` only ever writes a key it is handed, it never uploads anything itself. Left out of the write payload entirely when no new upload happened this session, so an unrelated save never touches the existing resume |
| `is_complete` | `saveProfile` | derived, see Key invariants |
| `cover_letter_tone` | never | out of scope for this feature by design |
| `created_at`, `updated_at` | never | database owned (default and trigger) |

**State transitions**: none. A profile has no lifecycle beyond "exists or does not yet exist" and "complete or not," both derived from its fields, not tracked as a separate state machine.

**API surface**:

| Action | Kind | Key inputs | Key outputs | Auth | Key errors |
|---|---|---|---|---|---|
| `uploadResumeFile` | Server Action | `file: File`, `previousUnsavedKey?: string` | `{ success: true, key: string }`, `key` is whatever storage actually assigned, not necessarily the requested path | signed in session, re-checked inside the action | not signed in, wrong file type, file over 5MB, empty file, upload failure. A failure to delete `previousUnsavedKey` is logged, never surfaced as this call's own failure |
| `saveProfile` | Server Action | the whole `Profile` object, plus `resumeKey: string \| null` | `{ success: true, isComplete, resumeKey?: string }`, `resumeKey` echoes what was written, unchanged from the input | signed in session, re-checked inside the action | not signed in, database write failure, database write of the whole row failed after a resume key was already supplied (returned as its own distinct message, since re-uploading is never the right retry in that case, only resaving) |

**Key invariants**:
- `is_complete` and the completion percentage and missing field list are always computed by the same one function, fed the same data, so they can never disagree with each other.
- The ten fields that count toward completion are: full name, phone, location, current title, experience level, years of experience, at least one skill, at least one work experience entry, a chosen highest degree, and at least one job title being sought. `percentage = round((10 - number missing) / 10 * 100)`. This exact set was chosen because it reproduces the delivered design's own example precisely: with phone, location, and education missing, seven of ten checks pass, which is exactly the 70% shown in `context/designs/profile.png`. The resume is not one of these ten fields, so uploading it earlier or later never changes a completion number or the `profile_completed` event.
- A work experience entry that was added but left entirely blank still counts as "at least one entry" under this rule. This is a known, accepted limitation of a simple presence check, not something to silently tighten later without a conscious decision.
- When `resumeKey` is null, `resume_pdf_url` is left out of the write payload entirely, not set to its current value and not cleared. An upsert with that key absent leaves the existing column untouched, so a normal profile edit can never accidentally wipe out an already stored resume.
- Selecting a resume uploads it to storage right away, through `uploadResumeFile`, independent of Save Profile. What still waits for Save Profile is only the database side: `resume_pdf_url` is not written, and no earlier saved resume is removed, until that click. `ProfileEditor` holds the resolved `resumeKey` as client state in between (see Decision).
- `saveProfile` reads the caller's current `profiles` row first, before making any change. This is what supplies the previous `resume_pdf_url` to delete on a replace, and the previous `is_complete` value AC-7's false to true transition check needs; the client never supplies either, since `Profile` deliberately carries neither field (see Feature design > Data model sketch above).
- Storage never overwrites an existing key; a second upload to the same path succeeds under a silently renamed key instead (confirmed directly against the live backend, see Rationale). Rather than depend on that behavior, each upload targets a fresh unique key, so there is nothing to collide with in the first place. Replacing an already saved resume is therefore: read the old key (from the pre read above), write the already uploaded new key to `resume_pdf_url`, then delete the old key. If that last delete fails, or if the row write fails after `resumeKey` was supplied, the newly uploaded object is simply left orphaned in storage; `resume_pdf_url` still correctly points at whichever resume is actually live, so neither failure ever produces a wrong or broken read, only unused storage. Cleaning up orphaned resume objects is out of scope for this feature (see Follow-up).
- A second, distinct orphan path now exists ahead of any save: a person selects a resume (uploads immediately), then either selects a different one before saving or leaves the page without saving at all. `ProfileEditor` covers the first case itself, best effort, by passing the earlier key to `uploadResumeFile` as `previousUnsavedKey` on the next selection. It cannot cover the second case (there is no reliable client side hook for "the person is leaving and never coming back"), so that upload stays orphaned; same accepted tradeoff as the database side orphan above, just reachable more often now that upload no longer waits for a click.
- A third variant of that same orphan: the upload can succeed on the server while its response never reaches the client (a dropped connection, a tab closed mid request). `ProfileEditor` never learns that key, so it can never appear in `previousUnsavedKey`, and the UI correctly shows the selection as failed even though an object was actually written. This is not a new class of problem, it is the same accepted "upload without a corresponding save" tradeoff as the point above, just triggered by the network instead of the person; no attempt is made to reconcile it (see Follow-up).
- Only one `uploadResumeFile` call is ever in flight at a time: `ResumeUpload`'s file input and dropzone are disabled for as long as an upload triggered by the current selection is unresolved (AC-9), so a second selection can never start before the first one settles. This is what keeps `previousUnsavedKey` correct; without it, two uploads racing could either leak the first (its key never makes it into state before the second fires) or let the older one win and get saved instead of the newer one.
- `ProfileEditor` only ever passes a key to `uploadResumeFile`'s `previousUnsavedKey` if that key has not yet been confirmed saved by `saveProfile`. Once `saveProfile` succeeds, the resolved key is a real, saved resume; deleting it is `saveProfile`'s own replace logic above, never a client side cleanup call.
- An upload that never settles (a hung request, not a fast failure) leaves the resume control disabled until the person reloads the page, the same way any other unresolved in flight request in this app is only ever recovered by a reload; no separate timeout or cancel affordance is added for this feature (see Follow-up).
- A staged, not yet saved `resumeKey`/`resumeFileName` pair is mirrored into `sessionStorage` under `profile-staged-resume:${userId}` the moment an upload resolves, and cleared the moment `saveProfile` succeeds, the same two points where the React state itself changes; there is no third place this can drift out of sync from. Read exactly once, in a `useEffect` that runs after mount, never in the `useState` initializer itself and never read again for the rest of that render's lifetime; the initializer must stay `null`, matching what the server rendered, or the client's first render disagrees with the server's and React flags a hydration mismatch (see Decision).
- `ResumeUpload` needs no new prop or status concept to display a rehydrated resume correctly. It already renders purely from `isUploading`, `uploadedFileName`, and `uploadError`, nothing else; once the `useEffect` above sets `resumeFileName` to the rehydrated value, `ProfileEditor` is already passing that straight through as `uploadedFileName`, and `ResumeUpload` shows the same "uploaded, ready to save" state it would for any other successful upload, no rehydration specific branch needed anywhere.
- Rehydrating never re verifies that the staged key's object still exists in storage, or that no other tab already saved a different resume in the meantime. This is a deliberate, cheap accepted risk, not an oversight: `sessionStorage` is tab scoped, so a different tab can never have raced this one (see Decision), and nothing in this project yet deletes a resume object out from under a live key (the orphan cleanup Follow-up item is not built). If that cleanup is ever built, it must not delete an object a live `sessionStorage` entry might still point to; noted as a dependency in Follow-up.
- Signing out does not need its own code to clear the staged entry. The next signed in user, in the same tab, reads a `sessionStorage` key namespaced by their own id, which was never written, so they see nothing staged; the previous user's entry is simply never read again, not actively deleted.

**Security model**: identical to every other authenticated page in this project. Row level security on `profiles` (spec 0001) already scopes every read and write to `id = auth.uid()`; nothing new is added here. Both `uploadResumeFile` and `saveProfile` re-check `auth.getCurrentUser()` themselves rather than trusting that they are only ever reached from the already auth gated `/profile` page, because a Server Action is directly callable over its own endpoint regardless of which page rendered the control that triggers it. The `sessionStorage` entry holds only a storage object key and a file name, the same, already not secret information a signed in person can already see rendered on their own screen; it is never a token or credential, and RLS still governs whether that key can actually be written to `resume_pdf_url` at save time regardless of what a tab's `sessionStorage` claims.

**Configuration required**: none. No new environment variables, secrets, or third party credentials.

**Critical test scenarios**:
- Happy path: select a resume (confirm it uploads immediately), edit several other fields, click Save Profile once, reload the page, every field and the resume key are still there, verifies **AC-1**, **AC-2**, **AC-4**.
- Failure case: two users' data never leaks into each other's row (RLS proves this, not application code), and a call to either action while not actually signed in is rejected with a clear error rather than crashing, verifies **AC-6**.
- Auth/permission: selecting a resume and leaving the page without clicking Save Profile leaves the `profiles` row untouched, though the object now exists, unreferenced, in storage, verifies **AC-8**.
- Replace before save: select a resume, wait for the upload to finish, select a different resume before clicking Save Profile, confirm the first upload's object no longer exists in storage, verifies **AC-8**.
- Save Profile and the resume control are both disabled while a just triggered upload is still in flight, so a second file cannot be picked before the first resolves, verifies **AC-9**.
- Survive a refresh: select a resume, wait for the upload to finish, reload the same tab, confirm the dropzone still shows it uploaded and ready to save without a second upload happening, then open the same page in a second, freshly signed in tab or session and confirm it starts with nothing selected, verifies **AC-10**.

## Consequences

**Positive**:
- The profile page becomes fully real; no more mock data anywhere on it.
- A resume selection gets fast feedback: a bad file or a failed upload surfaces right away, not only after the person has also filled in the rest of the form and clicked Save Profile.
- `ResumeUpload`'s dropzone copy ("click to upload or drag and drop") now matches what actually happens; the previous revision's small copy debt is resolved by this one, not carried forward.
- Completion logic lives in exactly one place, so the banner and the persisted flag can never quietly drift apart; this is unaffected by the resume timing change, since the resume is not one of the ten fields it counts.
- No migration risk: this feature only ever populates columns that already exist and are already covered by row level security.
- A refresh no longer costs a person their staged resume: within the same tab, an accidental reload used to always orphan the just uploaded file (the exact "leaving the page" tradeoff AC-8 describes); now the common accidental refresh case recovers cleanly instead, only a genuinely abandoned tab (closed, or never returned to) still orphans the upload.

**Negative / tradeoffs**:
- There is no longer one single mental model for "when does anything reach the server." The resume uploads to storage on select; every other field, and the resume's link to the profile row, still only persists on Save Profile. Two different moments to explain, where the first revision had one.
- Orphaned storage objects, already an accepted edge case failure path in the first revision, are now a routine outcome: any time a person selects a resume and does not go on to click Save Profile, one object is left behind. `ProfileEditor` cleans up the common "picked a different file before saving" case on a best effort basis, but a person who selects once and simply leaves the page always leaves that upload behind; no client side hook can catch that case. See Follow-up.
- `resume_pdf_url` holds an object key rather than a working link, so any future feature that wants to actually show or link to the resume (not just know it exists) needs to mint a signed URL at the point it is needed, not read the column directly.
- Two Server Actions instead of one to reason about for the resume specifically (`uploadResumeFile`, `saveProfile`), plus a little more state in `ProfileEditor` (an upload status alongside the resolved key) to coordinate them correctly.
- Storage never overwrites a key, so replacing an already saved resume is still a read, write, delete sequence at the database layer, and `saveProfile` still needs its own row read before it writes anything. If that delete fails after a successful replace, or the row write fails after `resumeKey` was supplied, one object is left orphaned in storage rather than actually removed; this never breaks correctness (the database always points at a real, live resume) but does mean each such failure leaves one small piece of unused storage behind, with no cleanup built into this feature.
- A third place to keep in sync: `sessionStorage`, alongside `ProfileEditor`'s React state and the database. The two write points (a successful upload, a successful save) are the same points the React state already changes at, so there is no new place this can drift, but it is one more thing a future change to this component has to remember to touch.

**Neutral**:
- `context/library-docs.md`'s InsForge Storage and DB Queries examples were corrected by `/sync` (see Follow-up); this spec did not edit that file itself.

## Follow-up

- [x] `storage.upload()`'s behavior on re-uploading to an existing key: confirmed by testing directly against the live backend's `PUT /api/storage/buckets/:bucket/objects/:key` endpoint (the exact call the SDK's `upload()` makes) with a real duplicate upload. It does not overwrite or error; it silently succeeds under a renamed key (`resume.pdf` then `resume (1).pdf`, and so on), and the response's `key` field is the only reliable source of truth for what a file actually got saved as. The same test showed the returned `url` needs the caller's own auth to resolve (an anonymous fetch of it returned 401), consistent with the bucket being private; this design never persists that `url` at all, only the key, so its exact expiry was not further pinned down as it does not matter to this feature.
- [x] `context/library-docs.md`'s InsForge Storage and DB Queries sections corrected by `/sync`: `.upload()` takes no `{ contentType, upsert }` options object and never overwrites an existing key (it renames on collision instead), `getPublicUrl()` only works for a public bucket so `createSignedUrl()` is the correct pattern for this project's private `resumes` bucket, and the DB accessor is `insforge.database.from(table)`, not the nonexistent `insforge.from(table)`. Root `AGENTS.md`'s own "persist both the url and key" line and `context/build-plan.md`'s feature 06/08 text were corrected too, for the same reason.
- [ ] Consider a periodic or manual cleanup pass for orphaned resume objects. This is now the more likely of the three orphan paths (see Consequences and Feature design > Key invariants): a resume uploaded on select whose page is left without ever clicking Save Profile, an upload whose success response never reached the client, or the older row write / post write delete failures carried over from the first revision. All are low priority: they cost storage space, never correctness, since `resume_pdf_url` always points at a real, live resume either way. If this is ever built, it must not delete an object a live `sessionStorage` staged entry (the third revision, AC-10) might still point to; a short grace period (skip anything uploaded in, say, the last day) would be the simple way to stay safe without having to read `sessionStorage` from a server side job.
- [ ] No timeout or cancel affordance exists for a resume upload that never settles; the resume control just stays disabled until the page is reloaded. One upload did fail this way during `/debug` (a 2MB file, isolated at the time to something in the Next.js Server Action file relay rather than the SDK or S3), but four fresh attempts at the identical file afterward all succeeded, so it looks like a one off, not a reproducible hang. Still worth adding a timeout or cancel affordance if this recurs; not built now since there is no evidence of a real, repeatable pattern.
- [x] Cover Letter Tone resolved for the current profile UI: the delivered design has no field for it, so `context/build-plan.md`, `context/architecture.md`, and `context/ui-registry.md` now treat `cover_letter_tone` as a reserved nullable DB column only.
- [ ] `jobTitlesSeeking` and `preferredLocations` are stored as arrays but edited as single comma separated text fields. This is a reasonable trade for now; if either field ever needs real per item structure (matching, filtering, tag style editing like Skills already has), that is its own future decision, not something this spec resolves.
