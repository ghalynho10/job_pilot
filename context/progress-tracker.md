- 06 Profile Save Logic designed via `/architect` and recorded at `docs/specs/0002-profile-save-logic/` (spec 0002, status Proposed, not yet built). Decision: one combined Server Action, `saveProfile(profile, resumeFile)` in `actions/profile.ts`, that saves every form field and, when a new resume was selected, uploads it too, all in a single call triggered only by the Save Profile button. Revised in session from an initial "upload the resume immediately on select" design after the engineer asked directly for the resume to save together with the rest of the form. - Spec 0002's storage design revised a second time during `/develop`'s own pre build check: directly tested (not assumed) the live `PUT /api/storage/buckets/:bucket/objects/:key` endpoint the SDK's `upload()` actually calls, by uploading twice to the same key. Confirmed storage never overwrites, it silently renames on collision, and an unauthenticated fetch of the returned `url` gets a 401 (matches the bucket being private). Final design: each resume upload targets a fresh unique key rather than a fixed path, `saveProfile` reads the caller's current row first (supplies the previous resume key plus the previous `is_complete` for the `profile_completed` transition check), and a replace is upload new, write it, then delete the old key, so a failed upload or write never costs the user their existing resume. A cross check on a different model (Opus) caught one real gap in that revision (nothing said where the "previous key to delete" came from) before it went further, fixed by the row read above.
